# 01. 게임·데이터·평가 원칙

## 만들려던 것

게임 화면을 보는 에이전트가 처음에는 창이나 룬을 완벽하게 모르더라도, **조작 결과로 정체를 확인한 뒤 다음 화면에서 더 잘 찾도록** 만들고자 했다. 이를 위해 한 단계의 `탐지율` 대신 네 질문을 나눴다.

1. 전체 화면에서 후보의 **위치**를 찾는가.
2. 여러 후보 중 **목표의 정체**를 맞히는가.
3. 레벨업·이펙트 변화 뒤에도 **같은 부모 창**으로 잇는가.
4. 게임의 성공·실패 피드백으로 학습해 **미래 세션에서 개선**되고, 부재·이전 상태에서도 안전한가.

## 두 게임과 데이터

`index.html`은 70칸 보드의 룬 수집 게임이다. 네 종류의 진짜 룬과 비슷한 가짜 룬을 둔다. 초기 비교는 게임에서 내보낸 45화면을 훈련 6·검증 3·테스트 6 **세션**으로 나눴다. 룬 crop 인식과 70칸 검색이 주요 과제였다. 화면의 임의 좌표 검출은 아니었다.

`upgrade.html`은 세 창 중 목표인 특성 강화 창을 찾고 레벨을 올리는 게임이다. 1~10레벨과 11레벨 이후의 내부 이펙트·레벨 표기·진행 영역이 달라진다. `effect`, `layout`, `layout_mimic` 조건으로 내부 외형과 배치를 바꿀 수 있다. 게임이 창 ID·요소 상자와 클릭 성공 여부를 기록하므로 실험에는 정답이 있지만, **평가용 렌더러 정답을 추론기의 입력으로 주지 않았는지**를 실험마다 따로 확인했다. 일부 실험은 세 창의 고정 슬롯 crop을 입력으로 줬고, 일부는 전체 화면을 입력으로 줬다.

## 비교에서 고정해야 할 것

| 평가 단위 | 입력 | 주요 지표 | 주의 |
| --- | --- | --- | --- |
| 룬 후보 식별 | 동일한 칸 crop | PR AUC, 룬 재탐지, 화면당 오탐 | 후보 위치를 이미 안다 |
| 부모 창 후보 탐지 | 전체 화면 | IoU 기준 후보 회수·여분 상자 | 목표 ID를 맞힌 것이 아니다 |
| 목표 창 선택 | 주어진/찾은 여러 부모 후보 | 올바른 Top-1, 부재 오탐 | 강제 Top-1과 행동 허용은 다르다 |
| 자식 영역 경계 | 부모 crop/전체 화면 | IoU, 선택된 상자, 후보 중 최선 | 의미·정체성은 별도 |
| 온라인 갱신 | 확인 전→확인 후 미래 세션 | 개선량, 옛 상태 회귀, 오탐·비용 | 확인된 것만 학습한다 |

훈련·검증·테스트는 **세션 단위**로 나누고, 임계값·모델 선택은 검증에서 끝내야 한다. 그러나 같은 렌더러라 픽셀 중복이 남았다. 초기 룬 테스트 양성 66 crop 중 20개는 누적 훈련 crop과 완전히 같았다. 후속 공통 후보 비교의 첫 단계에서도 5개가 같았다. 여러 레벨/변형이 같은 세션에서 나왔으므로 신뢰구간은 프레임이 아닌 세션을 재표본해야 한다. 보고서가 이미 탐색에 쓴 테스트를 다시 본 경우에는 봉인된 최종 테스트로 부르지 않는다.

## 모델의 역할 분리

OpenCV·YOLO·DINO 스캔은 **후보 위치**를 제안할 수 있다. DINOv2/v3는 주로 crop의 특징을 추출했고, Exemplar·개체별 Adapter·선형 분류기는 **이미 제안된 후보의 정체**를 판별했다. OmniParser V2 `icon_detect_v3`는 **내부 박스 후보**를 냈다. 시간 연속성·게임 행동 영수증은 이미지 모델 밖의 확인 근거다. 이 역할들을 한 점수로 합쳐 ‘어느 모델이 최고’라고 결론 내리지 않는다.
